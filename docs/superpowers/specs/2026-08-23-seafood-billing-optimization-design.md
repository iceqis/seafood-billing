# 海鲜批发记账系统优化设计

## 1. 文档目的

本设计用于指导海鲜批发记账系统的第一轮正式优化。目标是在不改变现有业务流程、不调整飞书多维表格结构、不迁移历史数据的前提下，解决当前版本的稳定性和安全问题，并建立可维护、可测试、可自动发布的工程基础。

本轮采用“渐进式模块化”路线：继续使用原生 HTML、CSS、JavaScript、Cloudflare Workers、GitHub Pages 和飞书多维表格，不引入 React、Vue 或新的业务数据库。

## 2. 当前系统基线

当前生产系统由以下部分组成：

- GitHub Pages：托管单文件前端页面。
- Cloudflare Worker：提供 REST API，并代理访问飞书开放平台。
- 飞书多维表格：保存客户、供应商、商品、销售订单和进货记录。
- GitHub 公开仓库：当前只包含 `index.html` 和简单的 `README.md`。

已经确认的主要问题包括：

1. 前端加载函数引用不存在的 `loading-text` 元素，阻断初始化和页面数据加载。
2. `/api/orders/*` 通用路由位于统一开单和结算路由之前，导致两个批量接口被错误处理。
3. 普通订单接口没有统一把飞书中文状态转换为前端英文状态值。
4. Worker 没有登录鉴权，且允许任意来源跨域访问。
5. 前端把业务数据直接拼入 `innerHTML` 和内联事件，存在页面注入风险。
6. 单号使用总记录数加一生成，删除记录或多人同时录入时可能重复。
7. 飞书记录读取没有处理分页，超过单页上限后统计和历史查询可能不完整。
8. 前端、Worker 和需求文档的版本标记缺乏统一管理。

## 3. 已确认的产品决策

- 保留现有技术栈，但拆分代码并补充测试、鉴权和部署流程。
- 采用全店统一密码，不建立员工独立账号和角色权限。
- 用户登录成功后保持登录30天，令牌过期、主动退出或管理员轮换安全密钥后重新登录。
- 推送到 `main` 分支后，自动测试并部署 Cloudflare Worker 和 GitHub Pages。
- 完全兼容现有五张飞书表，不新增字段、不修改字段、不迁移历史数据。
- 飞书多维表格继续作为唯一可信的业务账本。
- 页面上的列表、金额、状态和统计展示均从飞书业务数据获取。
- 本轮不增加利润报表、打印、多门店、离线同步等新业务能力。

## 4. 目标架构

### 4.1 总体数据流

```text
用户页面操作
    ↓
前端页面模块
    ↓
统一 API 客户端
    ↓
Cloudflare Worker 路由与鉴权
    ↓
参数校验与业务服务
    ↓
飞书字段适配层
    ↓
现有五张飞书多维表格
```

新增、修改、发货、定价、统一开单、结算和删除操作成功后，前端重新读取相关飞书数据并刷新页面。前端内存数据只用于当前页面展示，不作为正式账本。

### 4.2 前端目录设计

```text
index.html
assets/
  css/
    base.css
    components.css
    pages.css
    responsive.css
  js/
    app.js
    config.js
    api-client.js
    auth.js
    state.js
    utils.js
    pages/
      home.js
      preorder.js
      orders.js
      customers.js
      purchases.js
      products.js
      profile.js
```

文件职责如下：

- `index.html`：只保留页面骨架、语义结构和模块入口。
- `base.css`：颜色、字号、间距、基础元素和可访问性规则。
- `components.css`：按钮、卡片、状态标签、弹窗、提示和加载组件。
- `pages.css`：各业务页面的布局样式。
- `responsive.css`：手机、平板和电脑断点规则。
- `app.js`：应用初始化、导航和全局生命周期。
- `config.js`：非敏感环境配置，例如 API 地址和版本号。
- `api-client.js`：请求头、登录令牌、超时、错误转换和统一响应处理。
- `auth.js`：登录页面、令牌保存、登录状态检查和退出登录。
- `state.js`：当前页面所需的临时内存状态。
- `utils.js`：日期、金额和安全文本处理等纯函数。
- `pages/*`：各页面的数据加载、事件处理和渲染逻辑。

页面渲染优先使用 `textContent`、显式 DOM 节点和事件监听器，不把用户或飞书数据拼接进内联 JavaScript。

### 4.3 Worker 目录设计

```text
worker/
  index.js
  auth.js
  feishu-client.js
  field-mappers.js
  validation.js
  response.js
  services/
    customers.js
    suppliers.js
    products.js
    orders.js
    purchases.js
    statistics.js
```

文件职责如下：

- `index.js`：精确路由、CORS、鉴权入口和全局异常处理。
- `auth.js`：密码摘要验证、登录令牌签发和令牌校验。
- `feishu-client.js`：飞书 Token 缓存、分页读取和通用 CRUD。
- `field-mappers.js`：飞书中文字段、前端模型、状态和日期转换。
- `validation.js`：请求体、数值、日期、状态和批量操作校验。
- `response.js`：统一成功与失败响应格式。
- `services/*`：各业务域的规则和飞书读写编排。

路由必须按精确程度排序。`/api/orders/bill` 和 `/api/orders/settle` 必须在 `/api/orders/:id` 之前注册，禁止使用会提前吞掉特定接口的宽泛判断。

## 5. 飞书数据兼容设计

### 5.1 五张表保持不变

继续使用：

- 客户表
- 供应商表
- 商品规格表
- 订单表
- 进货表

所有中文字段名、字段类型和已有记录保持不变。系统不会自动创建、删除或修改飞书字段。

### 5.2 状态转换边界

飞书订单状态保持中文：待发货、已发货、未开单、未结算、已结算。

前端和 Worker 业务层统一使用：

- `pending_ship`
- `shipped`
- `pending_bill`
- `unsettled`
- `settled`

中文与英文的转换只发生在 `field-mappers.js`。API 不再向前端返回中文状态值，避免不同页面自行转换产生差异。

### 5.3 查询与统计

飞书记录读取必须循环处理分页，直到 `has_more` 为假。首页统计、客户未结金额和明细页面不能只依赖第一页数据。

金额计算统一在 Worker 中使用数值校验并保留两位小数。飞书公式金额存在时优先读取公式结果；公式结果为空时，使用重量乘单价计算展示值。

### 5.4 单号

保留 `XSD + YYYYMMDD + 序号` 和 `CGD + YYYYMMDD + 序号` 的可读格式。生成序号时查询当日同类单据的最大序号，而不是使用全表总记录数；创建前检查候选单号，发生冲突时重新分配。前端提交期间锁定保存按钮，降低重复点击和并发冲突。

## 6. 登录与安全设计

### 6.1 登录流程

1. 未登录用户只能访问登录界面。
2. 前端通过 HTTPS 将统一密码发送到 `/api/auth/login`。
3. Worker 使用 PBKDF2-SHA-256 加盐密码摘要进行恒定时间比对，不保存或记录原始密码。
4. 验证成功后使用 HMAC-SHA-256 签发有效期30天的签名令牌。
5. 前端只把签名令牌保存在当前站点的 `localStorage`，不保存原始密码，并通过 `Authorization: Bearer <token>` 调用业务 API。
6. 令牌过期或校验失败时，API 返回401，前端清除令牌并返回登录页。
7. 退出登录时清除当前设备令牌。

统一密码摘要和令牌签名密钥存放在 Cloudflare Secrets。管理员轮换签名密钥后，所有已有令牌立即失效。

### 6.2 API 保护范围

公开接口仅包括：

- `POST /api/auth/login`
- `GET /api/health`
- `OPTIONS` CORS 预检

客户、供应商、商品、订单、进货、统计和数据源检查接口全部需要有效登录令牌。

### 6.3 浏览器和跨域安全

- 生产环境只允许正式 GitHub Pages 域名。
- 本地开发地址只在开发配置中允许。
- 不在仓库中保存飞书 Secret、店铺密码或令牌签名密钥。
- 设置内容安全策略，只允许页面连接指定 Worker，不加载未知脚本。
- 所有业务数据在进入 DOM 前采用安全文本方式渲染。
- 删除、统一开单和结算操作保留二次确认。
- 登录接口配置请求频率限制，降低密码暴力尝试风险。

## 7. 错误处理与可恢复性

### 7.1 统一错误类型

前端至少区分：

- 400：填写内容不合法。
- 401：登录失效，需要重新登录。
- 403：来源或权限不允许。
- 404：记录不存在或已被删除。
- 409：状态冲突、重复单号或重复操作。
- 429：请求过于频繁。
- 502/503：飞书服务暂时不可用。
- 网络超时：没有收到 Worker 响应。

错误提示使用普通业务语言，例如“订单状态已经变化，请刷新后重试”，不直接向员工展示飞书原始报错和内部堆栈。

### 7.2 防重复和状态校验

- 提交后立即禁用对应按钮，响应结束后恢复。
- Worker 不相信前端传入的状态，执行发货、定价、开单和结算前重新读取当前记录。
- 仅允许文档定义的状态转换。
- 批量开单只接受同一客户且处于未开单状态的订单。
- 批量结算只接受处于未结算状态的订单。
- 批量操作返回成功数量、跳过数量和原因，避免部分成功却提示全部成功。

### 7.3 健康检查

- `/api/health` 只检查 Worker 代码是否能响应，不提前请求飞书 Token。
- 新增受保护的数据源检查接口，用于验证飞书凭证和五张表是否可访问。
- 日志记录请求编号、接口、状态码和耗时，不记录密码、令牌、联系电话和完整订单内容。

## 8. 测试设计

### 8.1 单元测试

覆盖：

- 中文与英文状态双向转换。
- 金额、重量、单价和日期校验。
- 订单状态转换规则。
- 密码摘要和登录令牌的有效、过期、篡改场景。
- 单号生成和冲突重试。
- API 错误到前端提示的转换。

### 8.2 API 契约测试

覆盖所有公开和受保护接口，重点验证：

- 未登录请求返回401。
- 登录成功和密码错误。
- `/api/orders/bill` 与 `/api/orders/settle` 命中正确处理器。
- 前端收到英文状态值。
- 批量开单不能跨客户。
- 非法状态转换返回409。
- 分页记录可以完整汇总。

### 8.3 前端交互测试

覆盖：

- 初始化时加载提示能够正常显示和关闭。
- 页面导航与数据刷新。
- 登录保持、过期退出和主动退出。
- 表单必填和数值校验。
- 保存按钮防重复点击。
- 空状态、加载状态、成功提示和错误提示。
- 业务文本不会被当作 HTML 或脚本执行。

### 8.4 端到端测试

使用模拟飞书数据完成：

```text
登录
→ 新建预订单
→ 发货录入实际重量
→ 定价并计算金额
→ 客户统一开单
→ 订单结算
→ 首页和客户统计更新
```

自动化测试不得写入生产飞书表格。正式数据验证使用受控的人工验收记录，并在验收后清理。

## 9. 自动部署设计

### 9.1 `main` 分支发布流程

```text
推送 main
  ↓
安装锁定版本依赖
  ↓
执行静态检查、单元测试、API 测试和前端测试
  ↓
部署 Cloudflare Worker
  ↓
检查 Worker 健康接口和登录保护
  ↓
部署 GitHub Pages
  ↓
检查首页、静态资源和 API 配置
```

任何测试失败时停止部署。Worker 部署或健康检查失败时，不继续发布前端。每次发布涉及的 API 变更必须先保持对当前线上前端兼容，避免 Worker 已更新而 Pages 尚未更新的短暂窗口影响员工使用。

### 9.2 密钥管理

- GitHub Secrets 保存 Cloudflare 部署凭证。
- Cloudflare Secrets 保存飞书凭证、店铺密码摘要和令牌签名密钥。
- 仓库只提供环境变量名称和配置说明，不提供真实值。
- 本地开发使用不提交到 Git 的环境文件。

### 9.3 回滚

每次生产部署对应一个 Git 提交。出现问题时恢复到上一个稳定提交并重新运行发布工作流。发布记录应包含提交编号、测试结果、Worker 部署结果和 Pages 部署结果。

## 10. 分阶段交付顺序

1. 建立基线：把当前线上前端、Worker 和需求文档纳入仓库并标记生产基线。
2. 修复阻断性故障：加载元素、路由顺序、状态转换和健康接口。
3. 拆分前端：按 CSS、公共模块和页面模块渐进迁移。
4. 拆分 Worker：建立路由、鉴权、飞书适配、校验和业务服务边界。
5. 加入统一密码登录和 API 保护。
6. 完善分页、单号、防重复、状态校验和批量操作反馈。
7. 建立单元、API、前端和端到端测试。
8. 配置 `main` 分支自动部署、发布检查和回滚说明。
9. 完成手机与电脑端易用性、性能和最终回归验收。

每个阶段必须形成独立提交，完成对应测试后再进入下一阶段。

## 11. 本轮不包含的内容

- 离线记账和网络恢复后自动同步。
- Excel、PDF 或图片账单导出。
- 利润、库存和商品销量报表。
- 蓝牙打印和电子发票。
- 多门店。
- 员工独立账号和角色权限。
- 飞书字段调整、表结构调整或历史数据迁移。
- React、Vue 等前端框架迁移。

## 12. 验收标准

满足以下条件后，本轮优化视为完成：

1. 现有五张飞书表及历史数据未被迁移或改变结构。
2. 登录后可以完成客户、供应商、商品、预订单、发货、定价、开单、结算和进货操作。
3. 页面展示的数据和统计来自飞书，并在业务操作后刷新。
4. 未登录用户无法读取或修改业务数据。
5. 订单状态转换、金额计算和批量操作结果准确。
6. 超过单页限制的数据仍能被完整查询和统计。
7. 手机和电脑端均可正常使用，大字和大按钮体验不退化。
8. 自动化测试覆盖关键业务流程并全部通过。
9. 推送 `main` 后能够自动部署 Worker 和 Pages，并执行发布检查。
10. 任一生产版本能够通过 Git 提交恢复到上一个稳定版本。
